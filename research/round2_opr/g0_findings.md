# G0: Outcome-Model Derivation and Feasibility Findings

Phase 1 of the OPR (Outcome-Probability Replay) task. This document freezes the
exact reading of `kit.py` outcome mechanics that the estimator in `opr_core.py`
implements, and records the five explicit determinations required by the task
spec. Written BEFORE any estimator implementation, so that later validation
results cannot retroactively reshape the derivation.

Source of truth: `kit.py` as of Round 2 close (git tree untouched; file hash
recorded in the run log).

## 1. Where outcomes live in kit.py

Three functions govern all outcome randomness:

1. `rand_for(seed, a, b, day)` -> `random.Random(f"{seed}:{a}:{b}:{day}")`.
   A fresh, deterministic PRNG instance keyed only by (seed, pair, day).
2. `_prob(state, t, rng, variant)` -> the acceptance gate and the shared
   latent draw `shared = rng.gauss(0, 0.45)`.
3. `Simulator.advance` -> consumes the first two gauss/uniform draws from the
   same `rng` in a fixed order (response days, acceptance, delays, date
   scheduling, happened flag, second-meeting events).

MSMI is defined in `Simulator.metrics`: a pair is an MSMI iff
`date_happened` is True, `date_day - assigned_day <= 30`, and BOTH members
have a `second_meeting_intention` event with value `'yes'` and
`occurred_day - date_day <= 3`. (The `on_time` variable computed in metrics
is dead code and plays no role.)

## 2. Exact conditional probability of one introduction being MSMI

Notation: introduction of pair (a, b) on day t in world with seed S and
variant V. Hidden attributes per member i: response rate `ra_i`, acceptance
bias `bias_i`, second-meeting bias `second_bias_i`, and a truth record with
weighted SOFT keys plus `relationship_goal`. Let

    fit(V)   = sum over keys k of w_k(V) * (1 if truth_a[k] == truth_b[k] else -0.5)
               w = relationship_goal .7, pace .4, lifestyle .25, conversations .2
               (shift variant: goal .25, pace .8, lifestyle -.25, conversations .5)
    drift(V,t) = -0.5 if V == 'drift' and t >= 35 else 0.0   [acceptance only]
    z_i(g)   = -0.25 + bias_i + fit(V) + g + drift(V, t)
    q_i(g)   =  0.15 + second_bias_i + g + 0.4 * (1 if goal_a == goal_b else 0)

with shared latent g ~ N(0, 0.45^2). Then, conditional on g:

    P(MSMI | g) = ra_a * sig(z_a(g)) * ra_b * sig(z_b(g))
                  * D(V)                      # P(date_day - t <= 30 | delayed structure)
                  * 0.78                      # happened flag
                  * prod_i in {a,b} [ ra_i * (3/5) * sig(q_i(g)) ]

where sig is the logistic function and D(V) is the exact deadline probability
computed in closed form (Section 3). Note: `drift` enters acceptance only, not
the second-meeting logit; and the shared `g` couples acceptance and
second-intention for BOTH members, so the product form above is NOT
factorizable into independent acceptance/second terms.

Unconditional P(MSMI) = E_g[P(MSMI | g)], a one-dimensional Gaussian
integral. No closed form for the integral itself; see Section 7 for the
deterministic quadrature plan.

## 3. Date-deadline probability, exactly

From `advance`: first-meeting response days `d1, d2 ~ U{1..7}` (rejection
loop if one accepts and the other declines is irrelevant here because MSMI
requires both accept). If both accept:
`base = max(d1, d2)`; with probability 0.62 the pair dates immediately with
`u ~ U{1..14}`, else with probability 0.38 a second delay `v ~ U{5..12}`
applies. Date day from introduction = `base + u (+ v)`.

Therefore:
- Non-delayed branch (prob 0.62): max possible = 7 + 14 = 21 <= 30 always.
  Conditional deadline probability = 1.
- Delayed branch (prob 0.38): deadline iff `d1 + d2_max + u + v <= 30` after
  taking max over d1, d2 — exact enumeration of the 7 x 7 x 14 x 8 discrete
  tuples (or, equivalently, of max(d1,d2) in {1..7} with its exact mass
  function: P(max=k) = (k^2 - (k-1)^2)/49).

    D(V) = 0.62 * 1 + 0.38 * P_delayed(max(d1,d2) + u + v <= 30)

computed by exact summation, independent of V (no variant scales delays in
kit.py). Precomputed constant; tests pin it against a brute-force enumeration.

## 4. Determination Q1: per-introduction stream independence — YES

Given (S, a, b, t, hidden attributes of a and b, V), the outcome draws of
one introduction are generated by `rand_for(S, a, b, t)` and are independent
of every other introduction's draws. Two introductions that share a day but
differ in pair, or share a pair but differ in day, use different Random
instances with distinct seeds and have independent streams. The ONLY
cross-introduction correlation channel inside a single `advance` call is the
shared latent g inside one pair's own acceptance/second coupling (Section 2).

## 5. Determination Q2: how other introductions CAN matter — trajectory only

Other introductions never change an introduction's outcome distribution
directly. They affect the trajectory, which changes WHICH introductions
happen later:

- A member introduced on day t is busy until t+8 (declines everything in
  between).
- A successful date on day D makes both members busy until D+6.
- Pause (both decline) retires a member for the rest of the episode.
- Policy feedback state (bands, history) is updated from outcomes and steers
  future pair choices — this is a policy-visible channel, not hidden
  outcome coupling.

Consequence for the estimator: p_msmi for a specific (pair, day, hidden-state)
tuple is well defined and stream-exact; summing p over a trajectory's
introductions is the correct expected-MSMI functional for that trajectory.

## 6. Determinations Q3, Q4, Q5

Q3 (computable without modifying kit.py): YES. The probability is a closed
form up to one Gaussian integral; the exact deadline probability is a finite
sum; the fit/drift/logit formulas are re-implementations of arithmetic that
`kit.py` performs internally. `opr_core.py` reads world structure from the
generated state (via `generate(seed, 200, 'evaluation', variant)` and the
internal rollout state, NOT via `observe()`) and recomputes probabilities
with its own code. `kit.py` is not edited and not imported by the estimator
beyond `generate`/`rollout` for world construction in research scripts.

Q4 (hidden fields required): per member — `response_rate`, `bias`,
`second_bias`, and truth (the four weighted SOFT keys plus
`relationship_goal` for the goal-match indicator); per world — `variant`
(absent from `observe()`); per introduction — day t (visible) and the pair
(visible). These exist in the raw generated world state; `observe()` never
exposes them.

Q5 (why hidden fields are barred at inference): `docs/DATA_CONTRACT.md` and
`docs/FAQ.md` state that reconstructing hidden state or random outcomes
inside a policy is prohibited and that only observable JSON is valid episode
input. Correct use in this task: hidden fields are research-time features of
the OFFLINE estimator only. The Phase 4 observable scorer, if built, trains
on decision-time observable features with the offline p as target; the
deployed policy (`policy.py`) never imports or calls anything in
`research/round2_opr/`.

## 7. Quadrature plan for E_g[P(MSMI | g)]

Stdlib only. Two implementations must agree to < 1e-10 absolute before any
validation numbers are trusted:

1. Gauss-Hermite with self-implemented nodes/weights (or, simpler and
   preferred: midpoint rule on a fine grid) over g in [-7*0.45, +7*0.45]
   with N points;
2. The same rule at N = 2N refinement, plus an independent trapezoid check.

Tail truncation at 7 sigma contributes < 1e-12 mass; harmless at this
tolerance. Both variants are covered in `test_opr.py`.

## 9. Feasibility verdict

OPR is FEASIBLE: the conditional probability is exactly computable from
read-only kit.py mechanics and sealed data exists for both calibration and a
variance-reduced pairwise comparison. Proceed to Phase 2 (implementation +
unit tests) and Phase 3a (preregistration before validation).
